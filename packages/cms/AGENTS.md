# Paquetes del CMS (`packages/cms/*`)

Lógica del CMS de datos integrado en la consola de super-admin (RF-09, ADR-011). Todos los paquetes se publican en el *workspace* como `@pymekit/cms-<nombre>`.

Aquí vive la API Hono del CMS (servicios Drizzle, rutas y esquemas Zod) y, desde F2.3, el código de cliente de su interfaz: el núcleo (`@pymekit/cms-ui-core`) y, desde F2.4, los paquetes de componentes del explorador de datos (`@pymekit/cms-filters`, `@pymekit/cms-table`, `@pymekit/cms-data-explorer-ui`). Las pantallas son rutas de la web (`apps/web/src/routes/admin/cms/**`) que cargan los datos y montan esos componentes, con la misma pila que el resto de la web (TanStack Router + Query, `@tanstack/react-form`, `@pymekit/i18n` con el *namespace* `cms`, `@pymekit/ui`). Las primitivas visuales genéricas que falten se añaden a `@pymekit/ui`, nunca a estos paquetes.

### Por qué el código de cliente va en paquetes aparte

Los componentes del explorador no pueden ir en `@pymekit/cms-data-explorer` (junto a sus rutas Hono) por dos motivos: los exports de ese paquete arrastran Drizzle y Hono, y `cms-ui-core` necesita importar los **tipos** de sus rutas para el cliente RPC, así que un componente allí que usara `cms-ui-core` crearía un ciclo de dependencias entre paquetes, que Turborepo no admite. El grafo queda en un solo sentido: `cms-data-explorer-ui` → `cms-filters`/`cms-table` → `cms-formatters/hooks` → `cms-ui-core` → (tipos de) `cms-data-explorer`. Ninguno importa código de servidor; la *build* de la web lo vigila con `serverLeakGuard`.

### Por qué `@pymekit/cms-ui-core` es un paquete aparte

El código de cliente reutilizable del CMS no puede vivir en los paquetes de funcionalidad (`cms-settings`, `cms-navigation`…): sus exports arrastran Hono, Drizzle y la clave secreta, y cualquier import de valor desde un componente acabaría en el *bundle* del navegador. Tampoco encaja en `@pymekit/cms-api`, que es el punto de montaje del servidor. Un paquete propio deja la frontera explícita: `cms-ui-core` solo importa `@pymekit/cms-api/client`, `@pymekit/cms-shared/error-codes` y **tipos** de rutas (`import type`), así que es seguro en el navegador; lo que depende de TanStack Start (el `fetch` isomorfo para el SSR) se inyecta desde la web (`apps/web/src/lib/cms/`). Su lógica pura tiene tests unitarios (`src/__tests__`).

Los *logs* usan `getLogger()` de `@pymekit/shared/logger`, igual que el resto de PymeKit.

## Cómo llega una petición

1. `apps/web/src/routes/api/cms/$.ts` (ruta de servidor de TanStack Start) recibe cualquier `/api/cms/*` y la reenvía a `createCmsApiApp()`.
2. `GET /v1/health` responde sin sesión.
3. Cabeceras de seguridad y CSRF de Hono (el CSRF global de la web solo cubre las *server functions*).
4. `registerAuthMiddleware` (`@pymekit/cms-auth/routes`): verifica el JWT con `getClaims()` (401 si no hay sesión), exige `app_metadata.cms_access = 'true'` (403) y que el usuario no esté bloqueado. Deja el cliente Supabase verificado en `c.get('supabase')`.
5. Se crean `c.get('drizzle')` (transacciones con los *claims* del usuario) y `c.get('authorization')`.
6. La ruta de la funcionalidad llama a su servicio.

## Cómo llega la interfaz a la API

1. El `beforeLoad` de `apps/web/src/routes/admin/cms/route.tsx` llama a `loadCmsAccess()` (`apps/web/src/lib/cms/cms-access.ts`), que pide `GET /v1/account` con `context.queryClient.ensureQueryData(cmsQueries.account())`. La respuesta trae la cuenta del CMS y `access` (secciones con permiso propio: `users`, `storage`, `auditLogs`). 401 → inicio de sesión; 403 con `errorCode = CMS_MFA_OR_INACTIVE_ACCOUNT` → aviso de verificación en dos pasos; otro 403 → 404.
2. Las consultas usan `cmsFetch` (`apps/web/src/lib/cms/cms-fetch.ts`, `createIsomorphicFn`): en el navegador es el `fetch` nativo contra `/api/cms`; durante el SSR se llama a la aplicación Hono **dentro del mismo proceso** reenviando la cabecera `cookie` de la petición entrante, sin salto de red.
3. La barra lateral de `/admin` (`apps/web/src/components/admin/admin-navigation.ts`) es una sola navegación por **áreas de negocio**, sin grupos «Plataforma»/«CMS»: «Inicio» (super-admin), una entrada plegable por área con sus tablas (`groupResourcesByArea` de `@pymekit/cms-ui-core/resources` sobre `/v1/navigation`, ya filtrado por permisos; en «Cuentas», el super-admin tiene además «Gestión de cuentas» → `/admin/accounts`) y, tras un separador, las herramientas (Usuarios, Archivos, Paneles, Auditoría, Ajustes) según `getCmsSectionVisibility()` y `/v1/account`, más el enlace «Todas las tablas». El área de cada tabla es un dato: `cms.table_metadata.ui_config.navigation_group` (máx. 60 caracteres), editable en Ajustes → Recursos (`PUT /v1/tables/:schema/:table`, campo `navigation_group`, mismo permiso `table:update`); las tablas sin área van a «Otros datos». Áreas por menor `ordering` y nombre; tablas por `ordering` y nombre visible.
4. El listado de una tabla (`/admin/cms/resources/$schema/$table`) valida la URL con `DataExplorerSearchSchema` (página, tamaño, búsqueda, orden, `filters` y `view`), la usa como `loaderDeps` y precarga la página con `ensureQueryData(cmsQueries.tableData(...))`; el componente la lee con `useSuspenseQuery`. Cambiar filtros u orden es navegar (`navigate({ search })`). Un 403/404 de la API se muestra como «no encontrado». Las mutaciones (vistas guardadas) usan `useMutation` + `invalidateQueries`.
5. La ficha de un registro tiene dos rutas: `.../record/$id` (clave de una columna; la columna se deduce del metadato de la tabla con `resolveSingleKeyColumn`, el mismo criterio que `buildResourceUrl`) y `.../record?col1=a&col2=b` (clave compuesta, validada con `parseRecordKeysSearch`). Ambas guardan en la URL la página de cada sección relacionada (`relatedPages`) y precargan con `loadCmsRecord` (`apps/web/src/lib/cms/cms-record.ts`) la ficha (`GET /v1/tables/:schema/:table/record`, que responde 403 sin permiso y 404 si la clave no existe) y las tablas legibles (`/v1/navigation`). Los permisos llegan a las relaciones por dos vías: la API solo resuelve las claves foráneas de tablas que el usuario puede leer (el resto se muestra sin enlace) y la ficha solo muestra secciones relacionadas de tablas legibles; cada sección vuelve a pedir sus filas al listado, que comprueba el permiso otra vez.

6. **Escrituras (F2.4c).** Crear (`.../$table/new`), editar (`.../record/$id/edit` y `.../record/edit?col=…`) y borrar. Los `loader` de las páginas de escritura comprueban el permiso (`loadCmsTableForCreate`, `loadCmsRecordForEdit`) y responden «no encontrado» sin él. La API (`packages/cms/data-explorer`, rutas de escritura) comprueba otra vez esquema protegido y permiso (403), exige que las condiciones de editar/borrar contengan la clave primaria o una restricción única (`conditionsIdentifyOneRecord`, 400) y traduce el SQLSTATE de las funciones `cms.*_record*` a un código estable (`RECORD_*` de `@pymekit/cms-shared/error-codes`) sin devolver nunca el texto de PostgreSQL (`classifyCrudError`). Las funciones SQL vuelven a comprobarlo todo, solo escriben columnas marcadas como editables y dejan la entrada de auditoría.

## Cómo añadir un *endpoint*

1. En el paquete de la funcionalidad, crea el servicio (clase + fábrica `createXService(c)`) que use `c.get('drizzle').runTransaction(...)`. Los algoritmos van en `lib/` o `utils/` como funciones puras, con tests.
2. Crea `registerXRoute(router: Hono)` con `router.get|post(...)('/v1/...', zValidator(...), handler)` y exporta su tipo (`export type XRoute = ReturnType<typeof registerXRoute>`) para el cliente RPC.
3. Expórtala desde `./routes` y regístrala en `registerFeatureRoutes()` de `packages/cms/api/src/server.ts`.
4. Añade un caso a `apps/e2e/tests/cms/cms-api.spec.ts` si cambia el control de acceso.

## Seguridad

- **Drizzle con *claims* por transacción.** `runTransaction` fija `request.jwt.claims`, `request.jwt.claim.sub` y el rol (`authenticated`/`anon`) con parámetros enlazados antes de cada transacción, así que Postgres aplica las políticas RLS del esquema `cms`. Nunca se interpola un valor del JWT en SQL.
- **`cms.verify_admin_access()` y RLS son la autoridad.** El *middleware* es solo la primera barrera: la base de datos comprueba además la cuenta activa del CMS y el MFA (aal2). Un super-admin con sesión aal1 pasa el *middleware* pero no ve datos.
- **Cliente administrador** (`getDrizzleSupabaseAdminClient`, `getSupabaseAdminClient`): ignora RLS. Solo después de comprobar permisos a mano y con un comentario que lo justifique.
- **Explorador de usuarios (F2.5):** usa la API de administración de Auth con la clave de servicio, así que cada acción comprueba antes el permiso `auth_user` y la protección del destino (`getUserProtection`: uno mismo, super-admin de la plataforma, personal del CMS o antiguo personal de rango igual o superior). Ningún *endpoint* escribe `app_metadata`; los esquemas Zod son estrictos y el acceso al CMS solo cambia con `cms.grant_admin_access`/`revoke_admin_access`.
- **Ajustes > Miembros y Autenticación (F2.7a):** leer miembros exige `account:select`; cambiar roles, `role:insert`/`delete` y las reglas de rango de `can_modify_account_role` (nunca uno mismo, solo roles y cuentas de rango inferior, nunca cuentas raíz); activar/desactivar va por `cms.set_account_active`. La obligación de MFA exige `system_setting:update` y aal2, y desactivarla, cuenta raíz (lo impone también el *trigger* `cms.guard_mfa_requirement_change`). Los rechazos se responden con `MEMBER_*`/`SETTINGS_*`.
- **Ajustes > Permisos (F2.7b):** una sola implementación de `/v1/permissions/**` (`@pymekit/cms-permissions`, `rbac-routes.ts` + `RbacService`). Leer exige `role:select` (roles) o `permission:select` (grupos y permisos); cada escritura comprueba antes lo mismo que la BD (`can_action_role`, `can_delete_role`, `can_modify_role_permission_group`, `can_modify_permission*`, `can_grant_permission*`) para responder con `PERMISSION_*`/`ROLE_*`/`GROUP_*`. Esquemas Zod estrictos sin `metadata`; no se crean permisos cuya capacidad no se tiene ni se borran roles con miembros. Los objetos de sistema del super-admin son inmutables (guardia `cms.guard_system_rbac_objects`, `55-cms-rbac-hardening.sql`).
- **Explorador de almacenamiento (F2.5):** valida *bucket* y rutas y exige `cms.has_storage_permission` sobre la ruta exacta de cada objeto antes de usar el cliente de servicio de Storage. Las subidas van por la API (límite de 5 MB, tipo de contenido decidido por el servidor: solo PNG/JPEG/GIF/WebP con firma válida se guardan como imagen), las URL firmadas caducan en 10 min (vista previa) o 1 min (descarga, con `Content-Disposition: attachment`).
- **Nunca** se importan rutas, servicios ni `@pymekit/cms-api/server` desde componentes o código de cliente: arrastran Drizzle, `postgres` y la clave secreta. Desde la interfaz solo se usa `@pymekit/cms-api/client` y los tipos de ruta con `import type`. El plugin `serverLeakGuard` de la web hace fallar la *build* si Drizzle o `postgres` acaban en un *chunk* del navegador.

## Variables de entorno

- `SUPABASE_DATABASE_URL`: conexión Postgres de Drizzle. Se lee en la primera petición; si falta, la web arranca y solo fallan las rutas del CMS.
- `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLIC_KEY`, `SUPABASE_SECRET_KEY`, `VITE_SITE_URL`: las mismas de la web.
- `PERF_LOG_LEVEL=on` (opcional): activa las trazas de rendimiento de las consultas.

## Verificación

- `pnpm --filter "@pymekit/cms-*" typecheck` y `pnpm --filter "@pymekit/cms-*" test:unit`
- Los tests heredados (`__tests__`) se ejecutan con Vitest, pero se excluyen del `typecheck` de su paquete: sus *fixtures* no siguen los tipos estrictos actuales.
